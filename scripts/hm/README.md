# H&M catalog import and recommendation inputs

These scripts use the manually extracted CSV files in `data/hm/`. The directory is gitignored. Keep the source files and all outputs local. No images are present in the current dataset directory.

1. Run the existing Medusa migrations and commerce seed against a **development database**. The seed must provide the `Online Store` sales channel, `Vietnam Warehouse` and shipping profile.
2. From the repository root, prepare a bounded catalog: `python scripts/hm/prepare.py --max-products 500`. This reads `articles.csv` and writes `data/hm/processed/catalog.jsonl` and `manifest.json`. The group key combines `product_code`, type, group, department and section because actual data contains conflicting attributes under the same `product_code`. Use `--max-products 0` only after the bounded import is validated and resources are sized.
3. With PostgreSQL/Redis available and the root `.env` configured, build the backend image with `docker compose build backend`. From the repo root run `docker compose run --rm --no-deps --volume ./data/hm/processed:/app/data/hm/processed --workdir /app/apps/backend backend npx medusa exec ./src/scripts/import-hm-catalog.ts`. The script uses Medusa product and inventory workflows, generates synthetic VND prices and inventory levels of 20 units per variant, and writes `data/hm/processed/medusa-mapping.jsonl`. Re-running skips products whose deterministic handles already exist and repairs missing inventory levels; it stops if an existing product has an incomplete article mapping. Do not use the native CLI without providing its database environment.
4. To prepare offline purchase interactions, set a private `HM_CUSTOMER_HASH_KEY` of at least 32 characters and run `python scripts/hm/prepare.py --max-products 500 --with-interactions`. This streams `transactions_train.csv`, writes pseudonymous `interactions.csv` for selected articles and article-level `popularity.json`, then updates the manifest. Keep the same secret for repeatable customer hashes; never commit or print it.
5. After import, run `python scripts/hm/build-popularity-candidates.py` to translate article popularity into Medusa product IDs. This generates an **offline artifact only**. It does not expose a Recommendation API or claim measured recommendation quality.

The CSVs have no reliable stock, current VND price, order grouping, login credentials or product view events. Synthetic price/inventory and H&M historical purchases are explicitly labeled in metadata and artifacts. No H&M transactions are imported as Medusa orders. The importer does not yet create category/collection taxonomy, ingest images or publish recommendation candidates into an online store. Those are subsequent phases of the implementation plan.

On 2026-10-31, the bounded 500-product catalog was imported into the local development PostgreSQL using the backend Docker Compose service, which provides `DATABASE_URL` and `REDIS_URL`. The native CLI attempts from `apps/backend` had lacked `DATABASE_URL` because it exists in the root `.env`, not `apps/backend/.env`; the reported pool error was misleading. PostgreSQL `max_connections` was restored to 100. Database verification found 500 published H&M products, 1,874 variants and 1,874 inventory levels. The mapping artifact has 1,874 unique article IDs. A second import created zero products and found all 500 existing products. This verifies the bounded sample, not the full dataset or storefront behavior.

Run the scripts only after checking the dataset's Kaggle competition rules and the intended use of its contents. The current directory has no `images/`; storefront product thumbnails will need permitted assets or placeholders.
